# cofa-plan — 방식 고르기와 작업 나누기

사용자가 **어떻게 동작하는지 이해한 상태로** 방식을 고르는 것이 목적이다. 고르기 전에는 확정하지 않는다.

## 1. 먼저 확인 (실행해서)
- 런타임: `python3 --version`, `node --version` 등 과제에 필요한 것만
- 설치된 패키지, 실행 포트·접속 방법 (README에 있으면 그대로)
- 남은 시간 (`.cofa/START` 기준)
- 비밀값은 존재 여부만 확인하고 값은 출력하지 않는다.

## 2. 핵심 방식 비교
과제의 가장 어려운 부분(결과를 좌우하는 처리)에 대해 A(가장 단순) / B / C(가장 정교)를 PLAN 표로 쓴다.
- **어떻게**: 전문 용어 없이 한두 문장. 용어를 써야 하면 괄호로 한 줄 정의.
- **예시 값 하나로 따라가기**: 작은 입력 하나가 어떻게 결과가 되는지 3~4단계로.
- 좋은 점 / 대가·약점 / 남은 시간 안에 되나.
- 세 방식 모두 BRIEF의 "만들 것"과 조건을 지켜야 한다. 합의된 기능을 빼는 안은 방식이 아니라 범위 변경이므로 표에 넣지 않는다.
- 추천 하나와 이유 한 줄을 쓰고 **"어느 방식으로 할까요? 고른 이유나 꼭 지킬 조건을 한 줄 같이 말해 주세요."라고 묻고 멈춘다.**
- "단순하게 해"라는 말은 구조를 단순하게 하라는 뜻이지 방식을 대신 고르라는 뜻이 아니다. 표를 보여주고 고르게 한다.

## 3. 사용자가 고른 뒤
1. `$cofa-decide`로 D-n: 고른 방식 / 내 말(사용자가 말한 이유 그대로) / 버린 대안과 차이 / 이유 / 적용 조건 / 한계·재검토 조건.
2. **구조**: 파일마다 역할 하나 — 데이터 읽기·검사 / 처리 규칙 / 화면·API / 설정값 정도로만 나눈다. 과제가 작으면 합쳐도 되고, 이보다 많은 계층·추상화는 만들지 않는다. 기존 코드가 있으면 그 구조를 따른다.
   - **설정값**: 담당자·README 조건으로 정해지는 값(기준값, 상한, 시간, 비율 등)을 PLAN "설정값" 표에 모으고 코드에서도 한 곳에 둔다. 담당자 답이 바뀌면 이 한 곳만 고치면 되고, 나중에 "이 값은 왜 이것인가"를 출처로 설명할 수 있다.
3. **데이터 흐름** 표: 입력 → 검사 → 처리 → 저장 → 표시. 파일·함수 이름은 예정으로 적는다.
4. **작업 목록** T-n: 입력→출력이 실제로 도는 가장 작은 단위. 필수 요구 하나가 끝까지 도는 작업이 맨 위.
   - 각 작업: 연결 요구(R-n) / 바꿀 파일 / 완료 확인(실행 명령과 기대 결과)
   - 화면 꾸미기·선택 기능은 필수 작업 뒤에 둔다.
5. **시간표**, **중간 점검 시각**(남은 시간의 절반쯤), **검증 시작 시각**(종료 30분 전)을 적는다.
6. 서브에이전트가 도움이 될 작업이 있으면 표시만 한다(예: "T-3 cofa-builder 후보 — 파일 겹침 없음"). 만들지는 않는다. 생성은 `$cofa-delegate`에서 사용자 OK 후.
7. PLAN 전체를 짧게 보여주고 OK를 받는다. OK를 받으면 상태를 `APPROVED (시각)`로 바꾼다.

## 끝나면
- 방식 표를 보여준 뒤에는 추천하지 않고 사용자의 선택을 기다린다.
- 계획 승인 뒤: `👉 다음 추천: $cofa-build T-1 — (작업 이름)`
  (서브에이전트 후보로 표시한 작업이 있으면: `또는: $cofa-delegate T-n — 이유`)

## 하지 말 것
- 고르기 전에 파일 만들기, 패키지 설치하기
- 원본 파일(데이터·README·형식 파일)을 바꿀 파일로 계획하기 — 필요하면 사용자에게 먼저 묻는다
- 요구에 없는 기능(로그인, 캐시, 확장 대비)을 작업 목록에 넣기 — 넣고 싶으면 "제안"으로 따로
- 한 작업에 여러 기능 몰아넣기
