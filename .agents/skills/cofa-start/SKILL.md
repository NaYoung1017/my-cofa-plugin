# cofa-start — 과제 파악 (코드 0줄)

목표는 해결책이 아니라 **무엇이 문제인지**를 사용자와 함께 정하는 것이다.

## 순서
1. **시간**: `.cofa/START`가 없으면 사용자에게 과제 시작 시각과 제한 시간(분)을 묻고 `HH:MM 제한분` 한 줄로 기록한다(예: `10:00 180`). README에 제한 시간이 있으면 그 값을 보여주고 확인만 받는다.
2. **원본 파일 목록**: 작업 폴더의 파일 목록과 크기를 본다(`.git`, `node_modules`, `.cofa`, `.agents`, `.codex`, `cofa-notes` 제외). 지시서 / 데이터 / 산출물 예시·형식 / 제공 코드 / 기타로 나눠 BRIEF "원본 파일" 표에 적는다. **이 파일들은 읽기만 한다.**
3. **지시서 정독**: 문장 단위로 뽑는다.
   - 제출 요구: 파일명·형식·위치·실행 방법·필수 문서(How_to_use 등)
   - 기능 요구: 누가(역할별) 무엇을 할 수 있어야 하나 → R-n
   - 제약·금지: 기술 스택, 외부 API, 데이터 사용 범위, 포트
   - 단서 조항: "다만·단·제외·예외·~한 경우에만" → 별도 요구로 뽑는다
   - 숫자 조건: 시간·거리·인원·기준값 → 원문 그대로
   - 평가 기준이 적혀 있으면 원문 그대로
4. **산출물 예시**: 형식(필드·단위·정렬·파일 구조)만 본다. 내용을 정답으로 가정하지 않는다.
5. **데이터**: `python3 .cofa/tools/profile.py <파일들>`을 실행한다. 파일을 통째로 열지 않는다.
   - 결과의 이상한 점을 **빠짐없이** BRIEF "데이터 이슈" 표(I-n)로 옮긴다: 위치(파일·열·행 수) / 무엇이 이상한가 / 원인 가설 / 결과에 미치는 영향 / 영향도.
   - **지시서의 숫자 조건과 실제 데이터가 어긋나는지 반드시 대조한다.** (예: "N 이내" 조건인데 N을 넘는 행이 몇 개인가)
   - 파일이 여럿이면 연결 키가 서로 맞는지(겹침 비율, 형식 차이) 본다.
   - 처리 방법은 정하지 않는다. 처리 칸은 `확인 필요`로 둔다.
   - 큰 데이터를 깊게 봐야 하면 `$cofa-delegate`로 `cofa-data`를 제안할 수 있다(사용자 OK 필요).
6. **모르는 것**: 지시서·데이터를 보고도 정할 수 없는 것을 **빠짐없이** "모르는 것" 표(U-n)에 적는다. 각각 답에 따라 무엇이 달라지는지와 영향도를 붙인다.
7. **기존 코드**: 실행 방법과 테스트 유무만 확인한다. 맞다고 가정하지 않는다.

## 영향도 매기기
- 높음: 답·처리에 따라 핵심 기능의 결과나 구조가 달라진다
- 중간: 일부 화면, 예외 처리, 표시 방식이 달라진다
- 낮음: 표현·편의 수준
영향도를 매긴 이유를 한 줄로 쓴다. 애매하면 높은 쪽으로 둔다.

## 사용자에게 보여줄 것
1. 과제 한 줄 요약 초안 (누가 · 무엇 때문에 · 무엇을)
2. 필수 제출물
3. **모르는 것 전부** — 영향도 순. 높음은 "답에 따라 달라지는 것"까지, 중간·낮음은 한 줄씩. 몇 개를 생략하지 않는다.
4. **데이터 이슈 전부** — 영향도 순. 높음은 위치·숫자·영향까지, 중간·낮음은 한 줄씩.
5. 개수 요약: `모르는 것 U 높음 n / 중간 n / 낮음 n · 데이터 이슈 I 높음 n / 중간 n / 낮음 n`
6. 영향도 높음 항목마다 처리를 정해 달라고 요청한다: 담당자에게 질문 / 가정으로 진행 / 처리 결정 / 영향 없음. 영향도 판단이 다르면 사용자가 바꾼다.
7. 문제 정의 한 문장을 직접 써 달라고 요청한다: `___이 ___ 때문에 곤란하다. 이번에 ___을 만든다. ___은 하지 않는다.`

사용자가 쓴 문장을 BRIEF.md 맨 위에 **그대로** 적는다. 초안을 원하면 서로 다른 관점의 초안 2개를 주고 고르거나 고치게 한다. 대신 확정하지 않는다.
사용자가 정한 처리는 표의 "처리" 칸에 적는다. 정하지 않은 높음은 `확인 필요`로 남긴다.
