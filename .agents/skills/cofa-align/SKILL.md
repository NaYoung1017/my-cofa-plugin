# cofa-align — 방향 맞추기

담당자의 말이 **요구 → 범위 → 우선순위**로 이어져야 한다. 이 스킬은 그 연결을 BRIEF에 정리하고 사용자 승인을 받는다.

## 모드 1 — 방향 정리 (구현 전, 또는 새 답이 왔을 때)

1. `BRIEF.md`, `INTERVIEW.md`, `DECISIONS.md`를 읽는다.
2. BRIEF의 "방향" 섹션을 채우거나 고친다.
   - 사용자와 장면: 누가, 언제, 어떤 순서로 쓰나 (역할별)
   - 성공 기준: 관찰하거나 실행해서 확인할 수 있는 문장 + 확인 방법
   - 이번에 만들 것: 중요한 것이 맨 위. 각 항목에 근거(README / Q-n)
   - 만들지 않을 것과 이유: 요청은 있었지만 시간·위험·우선순위 때문에 뺀 것
   - 지켜야 할 조건: 조건 / 예외·단서 / 출처(Q-n)
   - 모르는 것(U-n)·데이터 이슈(I-n) 처리 칸: 답을 받은 것은 Q-n, 가정으로 진행하는 것은 그 가정과 틀렸을 때 바뀌는 것
3. README가 정한 전제(웹 서비스, 역할 구분 등)는 그대로 둔다. 담당자 조건은 전제를 빼는 근거가 아니라 **방식을 정하는 조건**으로 읽는다.
4. 사용자에게 **바뀐 부분만** 보여준다: `이전 → 지금 (계기 Q-n)`. 처음이면 전체를 짧게.
   그리고 처리가 `확인 필요`로 남은 U-n·I-n을 **전부** 영향도 순으로 함께 보여준다. 높음이 남아 있으면 승인 전에 하나씩 처리를 정해 달라고 한다(질문 / 가정으로 진행 / 결정 / 영향 없음).
5. 승인을 물을 때 "빼거나 바꿀 것, 우선순위에 대한 생각이 있으면 한 줄 같이 말해 주세요"라고 덧붙인다. 사용자가 승인하면 버전을 올리고(v1, v2 …) "변경 이력"에 한 줄 남긴다. 범위·우선순위를 바꾼 것은 `$cofa-decide`로 D-n도 남긴다(사용자 말은 "내 말" 칸에 그대로).
6. (선택) 담당자 확인 메시지 초안: 개발 용어 없이, 만들 것 3줄 / 만들지 않을 것 2줄 / 확인 질문 1~2개. 보낼지는 사용자가 정한다.

## 사용자가 결정을 넘기려 할 때 ("알아서 해", "귀찮다", "빨리 만들어")
1. 대신 정하지 않는다. 이 말은 규칙 변경이 아니다(AGENTS.md 맨 위의 약속). 업무 규칙이 걸린 높음 항목을 AI 기본안으로 묶어 "전체 승인"을 추천하지 않고, 구현도 시작하지 않는다.
2. 대신 결정 부담을 줄인다:
   - 높음 항목을 같은 원인·같은 처리끼리 묶어 결정 횟수를 줄인다(예: 항목 5개 → 묶음 2개).
   - 담당자 한 번에 물을 질문 1~3개로 줄여 보여준다(`$cofa-interview`).
   - 중간·낮음은 한꺼번에 정하는 안을 낼 수 있다.
3. 사용자가 그래도 질문 없이 진행하겠다고 하면, 묶음마다 "가정으로 진행"할 내용을 **사용자가 고르게** 선택지로 보여준다. 고른 가정과 "담당자 미확인" 위험을 BRIEF 처리 칸과 D-n에 남긴다.
4. 계획 단계를 건너뛰려 하면 건너뛰는 것(방식 비교, 작업 나누기)과 위험(설명 못 하는 구현, 범위 초과)을 한 줄씩 보여주고 사용자가 고르게 한다.

## 모드 2 — 중간 점검 (PLAN의 중간 점검 시각, 또는 사용자가 요청할 때)

1. `PLAN.md` 작업 상태, BRIEF 요구 상태, 남은 시간(`.cofa/START` 기준)을 본다.
2. 세 줄로 보고한다: 끝난 것 / 남은 필수 / 위험(시간·`확인 필요` 항목·실패한 검증). 위험은 개수만 말하지 말고 항목을 전부 나열한다.
3. 시간이 모자라면 **범위 조정 선택지 2개**(무엇을 빼거나 줄이고, 무엇을 지키나)와 추천 한 줄을 내고, 고른 이유를 한 줄 같이 말해 달라고 한 뒤 멈춘다. 필수 요구를 빼는 안은 "범위 변경"이라고 명시한다.
4. 사용자가 고르면 BRIEF·PLAN을 고치고 `$cofa-decide`로 기록한다.

## 끝나면
- 방향 정리 뒤:
  - 영향도 높음 `확인 필요`가 남아 있으면: `👉 다음 추천: $cofa-interview — (항목) 질문`
  - 없고 PLAN이 아직 없으면: `$cofa-plan — 방식 고르기`
  - PLAN이 있는데 방향이 바뀌었으면: `$cofa-plan — 바뀐 조건으로 영향받는 작업 다시 보기`
- 중간 점검 뒤: `$cofa-build — 다음 작업 T-n` (범위를 줄였으면 줄인 뒤 첫 작업)

## 하지 말 것
- 근거 없는 조건이나 성공 기준을 지어내기 (모르면 U-n에 "확인 필요")
- 사용자 승인 없이 버전 올리기
- 방향 정리를 핑계로 구현 방식까지 정하기 (방식은 `$cofa-plan`)
