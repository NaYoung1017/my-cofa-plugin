# cofa-explain — 동작 방식과 이유 정리

제출 뒤 설명은 실제 구현과 대조된다. 목표는 사용자가 **파일·함수 이름을 대며 자기 말로** 설명하는 것이다. 모범 답안을 만들어 외우게 하지 않는다. 실제 후속 서술형이 시작되면 이 스킬을 쓰지 않는다.

## 1. 동작 지도 완성 (`cofa-notes/EXPLAIN.md`)
- 한 줄 요약: 누가 무엇을 넣으면 무엇을 거쳐 무엇이 나오나
- 동작 지도: 입력 → 파일:함수 → 출력, 5~8단계. 각 단계에 **실제 예시 값 하나**를 따라간다. 값은 실제로 실행해서 얻은 것만 쓰고 `(내가 봄)` / `(AI)` 꼬리표를 붙인다.
- 데이터 위치: 무엇이 어디에 저장되고, 누가 읽고, 누가 바꾸나

## 2. 결정 ↔ 코드 대조
`DECISIONS.md`의 각 D-n에 대해 기록된 선택이 실제 코드에 그대로 있는지 확인한다.
- 일치 / 불일치 / 코드 없음 으로 표시한다.
- 불일치면 어느 쪽이 맞는지 사용자에게 묻고, 기록을 고치거나("D-n 정정") 코드를 고칠지 사용자가 정한다.
- 코드 위치가 "예정"으로 남은 결정을 채운다.
- PLAN "설정값" 표의 값과 출처가 코드의 실제 값과 같은지도 대조한다.

## 3. 제출 문서 맞추기
- How_to_use 등 README가 요구한 문서를 실제 실행 방법·화면·기능과 대조한다. 없는 기능을 적거나, 있는 기능을 빠뜨리지 않는다.
- 과제가 준 형식 파일은 고치지 않는다. README가 정한 이름의 제출 파일(형식 파일의 복사본 등)에 쓴다. 형식 파일 자체를 채우라고 명시돼 있으면 사용자에게 먼저 확인한다.
- 문서를 고칠 곳을 찾으면 바로 고치지 말고 고칠 목록을 보여주고 OK를 받는다.
- 제출 문서가 여러 개이거나 길면 `$cofa-delegate`로 `cofa-writer` 초안을 제안할 수 있다. 그동안 메인은 1·2단계(동작 지도, 결정 ↔ 코드 대조)를 사용자와 한다. writer 초안은 메인이 근거 대조표를 확인하고, **사용자가 처음부터 끝까지 직접 읽는다**.
- 문서의 "왜 이렇게 만들었나" 부분은 DECISIONS의 내용만 근거로 쓴다.
- 한계와 실패 조건을 솔직하게 적는다: 어떤 입력·규모·상황에서 틀리거나 느려지나, 확인하지 못한 것은 무엇인가.

## 4. 막힌 부분 풀기 (사용자가 요청할 때)
1. 사용자가 "이 부분 모르겠어"라고 짚으면, 먼저 기록이 빠진 것인지 이해가 부족한 것인지 구분한다.
2. 작은 입력 하나를 정해 해당 코드를 단계별로 따라간다. 원리 한 문장 → 값 변화 3~5단계.
3. 사용자에게 자기 말로 다시 써 보게 하고, 사실과 다른 곳만 짚는다. 대신 써 주지 않는다.
4. 사용자가 쓴 설명을 EXPLAIN.md "내 말로 다시 쓴 것"에 그대로 남긴다.

## 끝나면
- 결정↔코드 불일치나 문서 불일치가 남았으면: `👉 다음 추천: (항목) 정리 — 기록을 고칠지 코드를 고칠지 고르기`
- 모두 맞으면: `python3 .cofa/tools/check.py 실행 → FAIL 0 확인 후 제출` (`FAIL(한계 D-n)`은 FAIL이 아니라 WARN으로 나온다. 제출 문서에 적었는지 확인한다)
