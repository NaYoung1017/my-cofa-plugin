# cofa-build — 확인하고 구현하기

## 1. 브리핑 (코드를 쓰기 전)
`PLAN.md`에서 다음 작업 T-n을 고르고(사용자가 지정하면 그것), 관련 파일만 읽은 뒤 아래를 보여주고 **멈춘다**.

```
[T-n] (작업 이름) — R-n
1. 할 일: (한 문장)
2. 파일·설치: 바꿀 것 a, b / 건드리지 않을 것 c / 설치: 없음 | 패키지명(이유)
3. 원리: (쉬운 말 2~3문장)
   예시) 입력 (작은 값) → (처리 1) → (처리 2) → 결과 (값)
4. 확인: `(실행 명령)` → (기대 결과)
5. 정할 것: (있으면 선택지 2개와 추천 / 없으면 "없음")
진행할까요? 바꿀 점이나 꼭 지킬 조건이 있으면 같이 말해 주세요.
```

- 처음 나오는 개념·라이브러리는 한 줄로 정의한다.
- 정할 것이 있으면 사용자가 고를 때까지 진행하지 않는다.
- 사용자가 OK와 함께 조건·이유를 말하면 그 조건을 구현에 반영하고, 결정이 걸린 것이면 `$cofa-decide` "내 말" 칸에 그대로 남긴다.

## 2. 구현 (OK 뒤)
- 브리핑한 파일만 고친다. 범위 밖 파일이 필요하면 멈추고 묻는다.
- 원본 파일(데이터, README·지시서, 산출물 예시·형식 파일)은 고치지 않는다. 산출물은 새 파일로 만든다. 사용자가 원본 수정을 허락한 경우에만 그 경로를 `.cofa/allow-edit.txt`에 한 줄 추가하고 `$cofa-decide`로 기록한다.
- 요구에 없는 기능·추상화·의존성을 추가하지 않는다.
- PLAN "구조"의 파일 역할을 따른다. 담당자·README 조건으로 정해지는 값(기준값, 상한, 시간 등)은 PLAN "설정값" 위치에만 두고 출처(Q-n / README)를 주석으로 단다. 코드 여기저기에 숫자를 직접 쓰지 않는다.
- 개인정보·비밀값을 코드나 로그에 넣지 않는다. 서버는 과제가 정한 포트·주소로 띄운다.

## 3. 실행과 보고
1. 실행 전에 기대 결과를 한 줄 말한다.
2. 확인 명령을 실제로 실행하고 출력을 그대로(필요한 줄만) 보인다.
3. 실패하면 원인 가설 1~2개와 확인 방법을 말하고, 고칠 방향이 두 가지 이상이면 사용자에게 고르게 한다. 같은 시도를 반복하지 않는다.
4. 보고 형식:
   ```
   [T-n 결과] 바꾼 파일: … / 실행: `명령` → 결과 / 판정: PASS | FAIL
   남은 것: … / 정할 것: …
   ```

## 4. 기록
- `PLAN.md` 작업 상태, `BRIEF.md` 요구 상태 갱신 (실행으로 확인했으면 done, 검증 전이면 doing)
- 작업 중 선택이 있었으면 `$cofa-decide` (AI 제안을 고치거나 거절했으면 `[수정]` 형식)
- `EXPLAIN.md` "동작 지도"에 이번에 생긴 `파일:함수 — 하는 일` 1~3줄 추가
- git이 있으면 바꾼 파일만 지정해 커밋: `git add <파일들> && git commit -m "T-n: (무엇) (R-n)"`. `git add .` / `-A`는 쓰지 않는다. push하지 않는다.

## 5. 서브에이전트
작업이 크고 다른 작업과 파일이 겹치지 않으면 `$cofa-delegate`로 `cofa-builder`를 **제안**할 수 있다. 사용자 OK 없이 만들지 않는다.

## 끝나면 (위에서부터 처음 해당하는 것 하나)
남은 시간을 `.cofa/START`와 `date +%H:%M`으로 계산해 함께 알린다.
- 남은 시간이 30분 이하이면: `👉 다음 추천: $cofa-verify — 남은 n분, 새 기능 대신 검증과 제출 준비` (FAIL이 있으면 고칠지, 한계로 기록할지 선택지도 함께)
- FAIL이면: `👉 다음 추천: 원인 확인 — (가설)` (고칠 방향은 사용자가 고른다)
- PLAN의 중간 점검 시각을 지났고 아직 점검하지 않았으면: `$cofa-align 중간 점검 — 남은 시간 n분`
- 남은 작업이 있으면: `$cofa-build T-(다음) — (작업 이름)`
- 작업이 모두 끝났으면: `$cofa-verify — 요구별 검증`
