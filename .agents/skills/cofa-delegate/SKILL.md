# cofa-delegate — 서브에이전트는 필요할 때만

메인 세션이 총괄이다. 사용자와 대화하고, 결정을 받고, 서브에이전트 결과를 다시 확인하는 것은 메인만 한다.
서브에이전트는 시간을 아끼거나 **독립된 눈**이 필요할 때만 쓰고, 불필요하게 늘리지 않는다.

## 1. 역할 (이 넷뿐)
| 역할 | 맡는 일 | 쓸 수 있는 파일 | 언제 |
|---|---|---|---|
| `cofa-builder` | 승인된 작업 카드 하나 구현과 완료 확인 실행 | 작업 카드의 "바꿀 파일"만 | PLAN 승인 뒤, 파일이 안 겹치는 작업 |
| `cofa-reviewer` | 끝난 작업(T-n)이나 전체 결과물을 구현자와 독립적으로 검수. 기대값을 먼저 정하고 실행해 대조, 재현한 문제만 보고 | `cofa-notes/reviews/` 아래 보고서만. 제품 코드·원본은 읽기만 | T-n이 done이 된 뒤 / `$cofa-verify` 때 |
| `cofa-writer` | ① 명세 모드: 담당자 답·결정이 BRIEF·PLAN의 어디를 바꾸는지 변경안 + 정합성 점검 → 사용자 승인 항목만 반영 ② 제출 문서 모드: README가 요구한 문서를 기록·실행 결과만 근거로 작성 | ① 승인 뒤 `BRIEF.md`·`PLAN.md`만 ② 카드에 적은 제출 문서만 | ① 구현 중 담당자 답·범위 결정이 생겼을 때 ② 검증 뒤 |
| `cofa-data` | 데이터 요약·이상값·조건 위반·파일 간 불일치 찾기. 처리 방법은 선택지로만 | `cofa-notes/data/` 아래 보고서만 | start 단계부터 |

모델·effort는 `.codex/agents/*.toml`에 정해 두었다: builder 6.1 Sol medium / reviewer 6.1 Sol high / writer 5.6 Terra medium / data 5.6 Terra medium. 메인은 사용자가 `/model`로 고른 모델(권장 6.1 Sol medium, 방식 비교·어려운 디버깅만 high)을 쓴다.

**메인이 하는 일**: 사용자와 대화(선택지·결정·"내 말" 받기), 담당자 질문 초안과 답 기록, 일 나누기와 카드 쓰기, 서브에이전트 결과 재실행 확인, 사용자에게 원리 설명, 시간 관리, 커밋, 10분 미만 작업 직접 처리. 서브에이전트끼리 직접 주고받지 않고 모든 전달은 메인을 거친다.

**한 작업을 만든 쪽이 그 작업을 검수하지 않는다.** builder가 만든 T-n은 reviewer가, 메인이 만든 T-n도 reviewer가 본다. reviewer가 찾은 문제를 고치는 것은 builder나 메인이고(사용자가 수정 방법을 고른 뒤), 고친 결과는 다시 reviewer나 메인이 재실행으로 확인한다.

## 2. 만들기 전 점검
하나라도 아니면 걸린 조건을 보여주고 메인이 직접 하기를 추천하며 멈춘다. 사용자가 그 조건을 보고도 만들라고 하면 `SUBAGENTS.md`에 "점검 미충족: (조건) / 사용자 이유: (말 그대로)"를 남기고 만든다. 단 "역할 넷뿐", "동시 3개", "역할당 1개(교체 1번)"는 넘지 않는다.

**상한**
- 동시에 돌아가는 서브에이전트는 최대 3개(역할별 1개).
- **역할당 1개를 만들어 계속 쓴다.** 다음 작업은 새로 만들지 않고 같은 에이전트에 후속 지시로 보낸다.
- 새로 만드는(교체) 경우는 둘뿐이고, 역할당 1번까지: (가) 이전 에이전트가 종료됐거나 후속 지시를 보낼 수 없다 (나) 맥락이 길어져 같은 실수를 반복하거나 이전 작업 내용을 섞는다. 교체할 때는 이전 에이전트의 마지막 보고 요약을 `SUBAGENTS.md`에 남기고, 새 에이전트에게는 카드만 넘긴다.
- 그래서 최대치는 생성 4개 + 교체 4번이고, 보통은 4개로 끝난다.

공통
- [ ] 맡길 일이 작업 카드 하나로 정의된다: 대상 / 읽을 파일 / 쓸 파일 / 완료 기준 / 금지
- [ ] 진행 중인 다른 작업과 **쓰는 파일이 겹치지 않는다**
- [ ] 같은 역할이 지금 작업 중이 아니다 (작업 중이면 끝난 뒤 후속 지시로 보낸다)
- [ ] 동시 3개 안이고, 새로 만드는 경우라면 역할당 1개(교체 1번) 안이다
- [ ] 결정이 필요한 일이 아니다 (결정은 사용자가 메인과 한다)

역할별
- builder: `PLAN.md`가 APPROVED이고, 메인이 직접 하면 10분 이상 걸린다
- reviewer: 검수할 T-n이 PLAN에서 done이고, **그 T-n의 파일을 지금 고치는 작업이 없다** (고치는 중이면 결과가 금방 낡는다)
- writer 명세 모드: 반영할 Q-n·D-n이 기록돼 있고, 그동안 **메인과 builder가 BRIEF·PLAN을 고치지 않는다** (반영이 끝날 때까지 builder에게 PLAN의 새 카드를 주지 않는다)
- writer 제출 문서 모드: 문서에 들어갈 기능이 VERIFY에 기록돼 있다(PASS든 FAIL이든). 남은 시간 30분 이하라 메인이 `$cofa-explain`을 해야 할 때 특히 쓴다
- data: 데이터가 커서 메인이 읽으면 맥락을 낭비한다

질문 하나, 파일 하나 읽기, 작은 수정은 맡기지 않는다.

## 3. 작업 카드 (역할별로 꼭 들어갈 것)
- builder: T-n / 연결 R-n / 바꿀 파일 / 완료 확인 명령과 기대 결과 / 금지
- reviewer: 대상 T-n(또는 "전체") / 연결 R-n과 조건 Q-n / 확인 명령 / 데이터 위치. **구현자의 보고·설명은 넣지 않는다**(독립 검수가 목적이다). 바뀐 파일 목록과 그 T-n의 커밋 해시(커밋 전이면 `미커밋`)는 넣는다
- writer 명세 모드: 첫 줄 `모드: 명세` / 반영할 Q-n·D-n 번호(INTERVIEW·DECISIONS 위치) / 사용자가 말한 범위·우선순위 조건 그대로
- writer 명세 반영 모드: 첫 줄 `모드: 명세 반영` / `사용자 OK: 변경안 n, m 반영` (사용자가 고친 내용이 있으면 그대로)
- writer 제출 문서 모드: 첫 줄 `모드: 제출 문서` / 쓸 문서 경로와 README가 정한 형식(형식 파일이 있으면 그 경로) / 근거 파일(BRIEF·DECISIONS·VERIFY·EXPLAIN) / 실행 방법 확인 명령
- data: 대상 파일 / 지시서의 숫자 조건 / 볼 질문

## 4. 제안 (사용자 OK 필요)
아래를 보여주고 멈춘다. 여러 개를 동시에 제안해도 되지만 OK는 각각 받는다.
```
서브에이전트 제안: cofa-reviewer (또는 builder / writer / data)
- 작업 카드: (3의 항목)
- 메인이 직접 하지 않는 이유: …
- 그동안 메인이 할 일: …
만들까요?
```

## 5. 생성
1. `cofa-notes/SUBAGENTS.md`에 한 줄 추가(역할, 카드, 상태 `진행`, OK 시각). 같은 에이전트에 후속 지시를 보낼 때도 카드마다 한 줄씩 추가한다(상태 `진행`, "후속" 표시).
2. 그 역할의 에이전트가 이미 있으면 **새로 만들지 않고 후속 지시로 카드를 보낸다**. 없을 때만 등록된 커스텀 에이전트 이름(`cofa-builder`, `cofa-reviewer`, `cofa-writer`, `cofa-data`)으로 생성한다. 등록이 안 보이면 기본 서브에이전트를 만들고 `.codex/agents/<이름>.toml`의 `developer_instructions`를 프롬프트 맨 앞에 그대로 넣는다.
   생성이 **모델 오류**(모델 없음·권한 없음 등)로 실패하면 사용자에게 알리고, OK를 받아 그 `.toml`의 `model`·`model_reasoning_effort` 두 줄을 지운 뒤 다시 만든다(메인 세션 모델을 쓴다). 설정 파일(`~/.codex/config.toml`)은 건드리지 않는다.
   서브에이전트 생성 자체가 안 되면 사용자에게 알리고, 원하면 **터미널 새 탭에서 Codex를 하나 더 열어** 같은 프롬프트를 붙여넣게 한다(이 경우에도 쓰는 파일이 안 겹쳐야 한다).
3. 위임 프롬프트에 다섯 가지를 모두 쓴다:
   - 목표: 이 작업이 끝나면 무엇이 되나 (요구 R-n)
   - 범위: 읽을 파일 / 쓸 파일
   - 금지: 범위 밖 수정, 패키지 추가, 다른 에이전트 생성, 결정 확정, commit·push
   - 완료 기준: 실행할 명령과 기대 결과 (reviewer는 "기대값 먼저 → 실행 → 대조")
   - 보고 형식: `.toml`의 보고 형식
4. 후속 지시에도 카드 다섯 가지를 다시 다 쓴다. 이전 작업 맥락에 기대지 않는다(reviewer에게는 "이번 대상은 T-n, 기대값부터 다시 정할 것"을 꼭 쓴다).

## 6. 결과 받기 (메인이 한다)
공통
1. 보고를 그대로 믿지 않는다. 바뀐 파일이 카드 범위 안인지 `git status --short --untracked-files=all -- . ':!.agents' ':!.codex' ':!cofa-notes'`로 본다. `git diff --stat`은 새 파일을 보여주지 않으므로 이것만으로 판단하지 않는다. 키트가 만든 `AGENTS.md`·`AGENTS.override.md`는 무시한다. git 저장소가 아니면 범위 점검은 NOT_RUN으로 적고 사용자에게 알린다.
2. 사용자에게 요약: 무엇이 됐나 / 실제 결과 / 정할 것. 선택지가 있으면 사용자가 고른다.
3. `SUBAGENTS.md` 상태를 `완료`로, "메인의 확인"에 다시 실행한 명령과 결과를 적는다. 결정이 생기면 `$cofa-decide`(결정자: 사용자, 근거에 "cofa-○○ 보고" 표시).

builder
- 완료 확인 명령을 메인이 **다시 실행**한다. 동작 원리를 `$cofa-build` 브리핑 형식(원리 + 예시 값)으로 사용자에게 짧게 설명한다.
- 그다음 그 T-n의 검수를 reviewer에게 맡길지 제안한다(4 형식).

reviewer
- FAIL로 보고된 항목은 메인이 그 명령을 **다시 실행해 재현**한다. 재현되면 `VERIFY.md`에 V-n으로 남긴다(확인자: `cofa-reviewer → 메인 재실행`). 재현 안 되면 "미재현"으로 적고 사용자에게 알린다.
- 문제마다 수정 선택지를 보여주고 사용자가 고르게 한다. 고친 것은 새 T-n(또는 기존 T-n 재작업)으로 PLAN에 넣고, `$cofa-decide [수정]`으로 남긴다: 계기 = reviewer가 찾은 것 / AI 제안 = 처음 구현 / 바꾼 것 / 근거 실행 결과.
- PASS 항목도 VERIFY에 옮긴다. reviewer가 NOT_RUN으로 둔 것은 PASS로 바꾸지 않는다.

writer 명세 모드 (변경안을 받았을 때)
- 변경안의 계기(Q-n·D-n)가 실제 INTERVIEW·DECISIONS 내용과 맞는지 메인이 확인한다. 답에 없는 조건이 끼어 있으면 그 항목은 빼고 알린다.
- 사용자에게 `$cofa-align`처럼 **바뀌는 부분만** 보여준다: 번호 / `이전 → 지금 (계기)` / 영향받는 작업. 정합성 점검에서 나온 문제도 전부 함께 보여준다. 사용자가 번호별로 반영·제외·수정을 고른다.
- 범위·우선순위가 바뀌면 `$cofa-decide`로 D-n을 남긴다(사용자 말은 "내 말"에 그대로).
- 보내기 전에 비교 기준본을 남긴다: `mkdir -p .cofa/before && cp cofa-notes/BRIEF.md cofa-notes/PLAN.md .cofa/before/` (두 파일이 커밋 전이면 `git diff`로 비교할 수 없다).
- 고른 번호만 `모드: 명세 반영`으로 writer에 보낸다.

writer 명세 반영 모드 (반영을 마쳤을 때)
- 메인이 `diff -u .cofa/before/BRIEF.md cofa-notes/BRIEF.md`와 `diff -u .cofa/before/PLAN.md cofa-notes/PLAN.md`로 **승인한 항목만** 바뀌었는지, BRIEF 버전과 변경 이력이 맞는지 본다. 승인 밖 변경이 있으면 되돌리고 알린다.
- 사용자에게 작업 현황을 보고한다: PLAN 작업 상태(재작업으로 todo가 된 T-n 포함) / `SUBAGENTS.md`의 진행 중 작업 / 남은 시간.
- 영향받는 builder·reviewer 카드를 바뀐 명세로 다시 쓴다. 진행 중인 builder 작업이 영향받으면 사용자에게 멈출지 계속할지 묻는다.

writer 제출 문서 모드
- "근거 대조표"에서 3곳 이상을 골라 근거 파일과 실제로 맞는지 메인이 확인한다. "실행 방법"은 메인이 그대로 한 번 실행한다.
- "기록과 코드가 다른 곳"이 있으면 `$cofa-explain` 2단계(결정 ↔ 코드 대조)로 넘겨 사용자가 어느 쪽이 맞는지 정한다.
- **문서는 사용자가 처음부터 끝까지 직접 읽는다.** 후속 질문은 제출된 문서에서 나온다. 사용자가 설명 못 하는 문장은 지우거나 사용자 말로 고친다.

data
- 숫자 몇 개를 메인이 `profile.py`나 짧은 명령으로 다시 세어 맞는지 본다. 발견은 BRIEF "데이터 이슈"(I-n)로 옮기고 처리는 `확인 필요`로 둔다.

## 끝나면
- 점검에서 걸렸으면: `👉 다음 추천: 메인에서 직접 — (해당 스킬)` (걸린 조건 한 줄, `또는: 그래도 생성 — 이유를 말해 주면 기록 후 생성`)
- 생성한 뒤: `👉 다음 추천: (그동안 메인이 할 작업) — 서브에이전트 결과가 오면 확인`
- builder 결과 확인 뒤: `$cofa-delegate cofa-reviewer T-n — 독립 검수` 또는 `$cofa-build T-(다음)`
- reviewer 결과 확인 뒤: FAIL이 있으면 `수정 방법 고르기 — (가장 영향 큰 문제)`, 없으면 다음 작업이나 `$cofa-verify`
- writer 명세 변경안 확인 뒤: 사용자 선택을 기다린다 (반영할 번호 고르기)
- writer 명세 반영 확인 뒤: `$cofa-build T-(재작업 또는 다음)` — 바뀐 명세 기준
- writer 제출 문서 확인 뒤: `$cofa-explain — 문서 직접 읽기와 결정 ↔ 코드 대조`
